# Product Requirements Document (PRD)

## Проект: appmetrica.online
**Версия**: 1.0 | **Дата**: 2026-10-13 | **Автор discovery**: AI Agent + владелец проекта (Vitalii Podolskii)

---

## 1. Executive Summary

### 1.1. В одном абзаце
appmetrica.online — внутренняя система аналитики приложений для одного владельца портфеля продуктов (iOS/macOS, Android, веб-сайты, Telegram-боты и бэкенды). Приложения отправляют системные события сессий (`session_start`, `session_end`) обычным HTTP-запросом на `https://i.appmetrica.online/v1/events` — без SDK, по документированному API с готовыми рецептами для каждой платформы. Система хранит события в собственном ClickHouse на выделенном сервере Hetzner в ЕС, склеивает устройства одного человека по `user_id` задним числом и показывает на одном экране портфель всех приложений, а внутри приложения — аудиторию, retention, realtime, профили и здоровье интеграции. Цель MVP (4–6 недель) — после 14 дней параллельной работы с Яндекс AppMetrica с расхождением DAU ≤ 5 % удалить AppMetrica SDK из всех приложений.

### 1.2. Тип продукта
Full-stack web (SaaS classic, internal single-user) + Backend API (публичный ingestion + Read API) — профили #3 и #4 из `references/project-types.md`. Tier: T1 по команде и ops (solo), T2 по объёму данных (10k–100k DAU, 10–150 млн событий в месяц).

## 2. Problem Statement

### 2.1. Какую проблему решаем
Владелец портфеля приложений не может получить полную и независимую картину аудитории всех своих продуктов без встраивания стороннего закрытого SDK и без зависимости от Яндекса.

Развёрнуто. Сегодня в мобильных приложениях владельца стоит SDK Яндекс AppMetrica. Владелец отметил все четыре боли из предложенных: (1) **SDK в сборке** — сторонний закрытый код, его вес, обновления, privacy manifest в App Store и Data safety в Google Play, риски модерации; (2) **зависимость от Яндекса** — данные у третьей стороны, надёжность сервиса и возможные ограничения для зарубежной аудитории; (3) **нет единой картины** — сайты, Telegram-боты и десктоп в AppMetrica не завести, у неё нет web и desktop SDK; (4) **сложность** — интерфейс перегружен, нужные цифры искать долго, нет одного экрана с главным по всем приложениям.

### 2.2. Как проблема решается сейчас (without our product)
- Мобильные приложения: Яндекс AppMetrica SDK (iOS, Android), отчёты в веб-интерфейсе AppMetrica по одному приложению за раз.
- Сайты, боты, бэкенды: аналитики нет совсем или она разрознена; единой цифры «сколько людей пользуется моими продуктами вчера» нет.
- Сверка между продуктами — вручную, переключением приложений в интерфейсе AppMetrica.

### 2.3. Что не так с текущими решениями
- **AppMetrica Post API не даёт работать без SDK**: принимает только идентификаторы, которые уже приходили через SDK, синхронизирует раз в 4 часа, принимает данные в query string или CSV ([00-references.md](./00-references.md#3-competitive-analysis-derived)).
- **Хрупкость внешнего сервиса**: 13.10.2026 все домены AppMetrica отдавали заглушку «технические неполадки»; при длительном превышении лимита AppMetrica останавливает приём кастомных событий.
- **Open-source аналоги не закрывают задачу целиком**: Aptabase не умеет retention (ID пользователя меняется ежедневно), Countly даёт retention только в платной версии от $175/мес, PostHog требует Kafka + Redis + Rust + Python для self-hosting, Umami и Plausible ориентированы на веб.
- **Облачные Mixpanel и Amplitude** — данные снова у третьей стороны и оплата за события.

### 2.4. Что случится, если мы НЕ построим
- SDK AppMetrica остаётся во всех сборках: каждый релиз тянет обновления SDK и декларации приватности; отказ от Яндекса откладывается бессрочно.
- Сайты и боты так и остаются без аналитики; решения по продуктам портфеля принимаются по неполным данным.
- Любой сбой или изменение условий AppMetrica (лимиты, тарифы, доступность) напрямую бьёт по видимости бизнеса владельца.

## 3. Goals & Success Metrics

### 3.1. Business Goals
- **Primary**: заменить Яндекс AppMetrica во всех приложениях портфеля собственной системой с сопоставимыми цифрами (DAU и новые ±5 %, D1 ±3 п.п.) и удалить AppMetrica SDK из всех приложений не позднее 3 месяцев от старта разработки (веха M6, 2027-01-22).
- **Secondary**: (1) подключить к той же системе все сайты, Telegram-боты и бэкенды портфеля, чтобы видеть «всех людей во всех продуктах» на одном экране; (2) держать стоимость владения в пределах одного сервера (≈ 266 €/мес) и ≤ 2 часов ops-работы владельца в месяц; (3) иметь Read API для собственных скриптов и ботов-сводок.

### 3.2. Success Metrics (после запуска)

| Метрика | Target 3 мес | Target 6 мес | Target 12 мес |
|---|---|---|---|
| Расхождение с AppMetrica в сверке (unit=installs): DAU и новые / D1 | ≤ 5 % каждый день / ≤ 3 п.п. на 14-дневном окне для 100 % приложений с SDK AppMetrica | Сверка завершена; регрессий метрик на фикстурных тестах — 0 | Регрессий метрик на фикстурных тестах — 0 |
| Доля мобильных приложений, из которых удалён AppMetrica SDK | 100 % (релизы без SDK прошли ревью сторов) | 100 % | 100 % (аккаунт AppMetrica не используется) |
| Доля продуктов портфеля (приложения + сайты + боты), отправляющих события | ≥ 80 % (все мобильные + основные сайты) | 100 % | 100 % |
| Доступность ingest `i.appmetrica.online` (месячная, по healthchecks.io и внешним проверкам) | ≥ 99.9 % | ≥ 99.9 % | ≥ 99.95 % |
| Время подключения нового приложения: от `createApp` до статуса «первое событие получено» | ≤ 30 мин | ≤ 20 мин | ≤ 15 мин |
| Доля отклонённых событий (rejected / (accepted + rejected)) по приложениям после интеграции | ≤ 0.5 % | ≤ 0.2 % | ≤ 0.1 % |

| Время владельца на ops (обновления, бэкапы, инциденты) в месяц | ≤ 3 ч | ≤ 2 ч | ≤ 1 ч |

### 3.3. North Star Metric
**Полнота портфеля** — доля продуктов портфеля, по которым к 09:00 по TZ владельца данные за вчерашний день полные: ingest без простоя за сутки, доля отклонённых событий < 0.5 %, дайджест доставлен в Telegram. Target: 100 % ежедневно начиная с 3-го месяца. Метрика вычисляется worker-ом (job `digest` + `system_check`) и видна на вкладке «Система» в `/settings`.

### 3.4. Non-goals (сознательно)
- Не оптимизируемся под количество отчётов и гибкость «конструктора»: фиксированный набор экранов S-01..S-14 важнее настраиваемых workspace-ов.
- Не оптимизируемся под внешних пользователей, регистрацию, биллинг и SEO — продукт внутренний, документация закрыта логином.
- Не гонимся за минимальной задержкой ответа ingest ценой надёжности: ответ 200 отдаётся только после подтверждённой записи в ClickHouse (P99 ≤ 500 мс допустим, клиенты шлют в фоне).
- Не оптимизируем мобильный просмотр дашборда: только десктоп от 1280px.

## 4. Users & Personas

### 4.1. Primary Persona: Владелец портфеля (solo-разработчик)

- **Demographics**: независимый разработчик и владелец нескольких продуктов: iOS/macOS и Android-приложения, SEO-сайты, Telegram-боты, серверные сервисы; аудитория продуктов 10k–100k DAU суммарно, в основном за пределами РФ.
- **Technical level**: expert — уверенно владеет Go, TypeScript/React, Linux/Docker/ops; ClickHouse не знает (нужны runbook-и и тесты SQL).
- **Goals**: каждое утро за 1–2 минуты понять состояние всех продуктов; быстро подключать новые продукты без SDK; проверять, что релиз не сломал интеграцию; отвечать на запросы удаления данных пользователей.
- **Pain points сегодня**: SDK AppMetrica в каждой сборке; зависимость от Яндекса; нет картины по сайтам и ботам; перегруженный интерфейс AppMetrica.
- **Успех для них выглядит как**: открыл `appmetrica.online`, вошёл по Face ID, увидел портфель с DAU, Δ к прошлой неделе и D1/D7 по каждому продукту; утром получил дайджест в Telegram, не открывая браузер; AppMetrica SDK удалён.
- **Frequency использования**: daily (утренний просмотр портфеля и дайджест), weekly (retention и разбивки по версиям), в дни релизов — realtime и экран «Интеграция».

### 4.2. Secondary Personas

- **AI-агент-реализатор** (Claude Code / ralphex loop): пишет код по тикетам [13-tickets.md](./13-tickets.md); ему нужны однозначные контракты ([06-api-contracts.md](./06-api-contracts.md)), схемы ([05-data-model.md](./05-data-model.md)) и проверяемые AC.
- **Клиентский код приложений владельца** (как «технический пользователь» API): Swift/Kotlin/JS/Go-код, который генерирует `install_id`, ведёт сессии, офлайн-очередь и ретраи по документации; ему нужны точные коды ошибок и флаг `retryable`.

### 4.3. Антиперсоны (НЕ для них)
- **Внешние разработчики и команды**, которые хотят зарегистрироваться и пользоваться сервисом: регистрации, тарифов и мультиаренды нет.
- **Маркетологи, которым нужна атрибуция, воронки и выручка**: эти отчёты out of scope MVP.
- **Пользователи, которым нужен мобильный дашборд или тёмная тема**: только десктоп, только светлая тема.

## 5. User Journey (Core Flow)

### 5.1. First-time user experience (FTUE)

```mermaid
flowchart LR
    A[Деплой на Hetzner через Dokploy] --> B[CLI: appmetrica admin passkey-link]
    B --> C[/setup/token: регистрация passkey]
    C --> D[Пустой портфель → «Добавить приложение»]
    D --> E[Экран «Интеграция»: ключ pk_ + сниппет]
    E --> F[Первое событие → статус зелёный: aha moment]
    F --> G[Портфель с данными, дайджест в Telegram: activation]
```

**Пошагово**:
1. Владелец разворачивает стек по [12-dev-runbook.md](./12-dev-runbook.md) и [21-ops-runbooks.md](./21-ops-runbooks.md): Dokploy-приложения `appmetrica-ingest`, `appmetrica-api`, `appmetrica-worker`, `appmetrica-web`, compose `clickhouse-stack`, managed Postgres.
2. Выполняет в контейнере api `appmetrica admin passkey-link` и получает одноразовую ссылку `https://appmetrica.online/setup/<token>` со сроком жизни 15 минут.
3. Открывает ссылку (S-02), вводит название устройства («MacBook Pro»), подтверждает Touch ID — создаётся владелец, passkey и сессия; редирект на портфель (S-03) в пустом состоянии.
4. Нажимает «Добавить приложение» (S-04): имя «Notes iOS», платформа `ios`, часовой пояс `Europe/Berlin` → создаётся приложение и первый write-ключ `pk_…`; редирект на «Интеграцию» (S-10).
5. Копирует сниппет curl с подставленным ключом, выполняет в терминале — статус «Ждём первое событие» сменяется на «Первое событие получено 12:04:31» за ≤ 10 секунд (**aha moment**).
6. Встраивает рецепт Swift из `/docs/recipes/ios-swift` в приложение, выпускает TestFlight-сборку; на вкладке «Интеграция» видит accepted-события по версии `2.4.0` и 0 отклонённых.
7. В `/settings` → Telegram указывает `chat_id`, включает дайджест на 09:00 и отправляет тестовое сообщение (**activation**: на следующее утро приходит дайджест, портфель показывает DAU).

### 5.2. Core action (happy path)

**Одно действие, ради которого продукт существует**: утром за ≤ 2 минуты понять состояние всех продуктов портфеля по портфелю (S-03) и/или дайджесту в Telegram, и при отклонении провалиться в отчёт конкретного приложения.

Как юзер его выполняет:
1. Открывает `https://appmetrica.online` (сессия жива 30 дней, idle 7 дней) — сразу видит портфель за «вчера» в environment `production`.
2. Сортирует по колонке «Δ к прошлой неделе», находит приложение с падением DAU на 12 % и кликает строку.
3. На странице «Аудитория» (S-05) включает сравнение с предыдущим периодом, открывает разбивку по `app_version` и видит, что падение сосредоточено на версии `3.1.0`; переходит на «Интеграцию» (S-10) и видит всплеск `invalid_field` у этой версии — причина найдена.

### 5.4. Error states & edge cases

| Ситуация | Что видит юзер | Recovery |
|---|---|---|
| Нет интернета | Баннер «Нет соединения с сервером» над контентом, данные последнего успешного запроса остаются на экране (TanStack Query cache), realtime ставится на паузу | Автоповтор при восстановлении сети (refetchOnReconnect); кнопка «Повторить» |
| Server error 5xx | В карточке отчёта: «Не удалось загрузить данные (503 storage_unavailable). Код запроса: <request_id>» | Кнопка «Повторить»; при `storage_unavailable` — ссылка на вкладку «Система»; алерт уже ушёл в Telegram от worker |
| Пустое состояние (empty data) | Портфель без приложений: «Пока нет приложений» + кнопка «Добавить приложение»; приложение без событий: «Событий ещё не было» + ссылка «Открыть интеграцию» | Переход к S-04 / S-10 |
| Загрузка (loading) | Skeleton-карточки и skeleton-строки таблицы размером с итоговый контент (без сдвига layout, CLS < 0.1) | — |
| Rate limit hit | Дашборд: toast «Слишком много запросов, повтор через N с»; клиент приложения: `429 app_rate_limited` + `Retry-After` или `install_rate_limited` (retryable) в теле 200 | Автоповтор после `Retry-After`; клиенты — по политике ретраев из доков |
| Auth expired | Любой 401 `unauthenticated` → редирект на `/login?next=<текущий путь>` | Вход по passkey, возврат на исходную страницу |
| Удалённый ресурс (deep link на архивное или удалённое приложение / профиль) | 404 `app_not_found` / `profile_not_found` → страница S-14 «Не найдено» со ссылкой на портфель | Переход на портфель |
| Диапазон слишком большой | 400 `range_too_large` → inline-ошибка у выбора периода «Максимум 366 дней (для почасовой детализации — 7 дней)» | Сократить период |

## 6. Functional Requirements

### 6.1. Must Have — P0 (MVP)

Все FR-001..FR-028 входят в MVP (FR-026…FR-028 добавлены 2026-10-14 по макету «Dashboard v2»). Детальные технические AC с test_path — в [02-tech-spec.md](./02-tech-spec.md); контракты — в [06-api-contracts.md](./06-api-contracts.md).

#### FR-001: Приём батча событий
**User story**: Как клиентский код приложения, я хочу отправить батч системных событий одним HTTP-запросом без SDK, чтобы аналитика работала на любой платформе.

**Acceptance criteria**:
- [ ] Given валидный ключ `pk_` в заголовке `X-App-Key` и батч из 2 событий `session_start` + `session_end`, When `POST https://i.appmetrica.online/v1/events`, Then ответ 200 `{"accepted":2,"rejected":[],"warnings":[]}` и оба события видны в `appmetrica.events`.
- [ ] Given батч из 3 событий, где у второго `install_id` не UUID, When запрос, Then 200 с `accepted=2` и `rejected=[{"index":1,"code":"invalid_field","field":"events[1].install_id","retryable":false}]`, а отклонённое событие записано в `rejected_events`.
- [ ] Given невалидный JSON, When запрос, Then 400 `invalid_json`; Given 501 событие, Then 400 `invalid_batch`; Given тело > 1 048 576 байт после распаковки, Then 413 `payload_too_large`.
- [ ] Given ключ передан полем `app_key` в теле с `Content-Type: text/plain` (sendBeacon), When запрос, Then события приняты; Given ключ в query string, Then 401 `missing_app_key`.
- [ ] Given ClickHouse недоступен, When запрос, Then 503 `storage_unavailable` с `Retry-After`, ответ 200 не отдаётся ни для одного события.

**Priority rationale**: Без приёма событий продукта нет.

#### FR-002: Коррекция часов и окно досыла
**User story**: Как владелец, я хочу, чтобы события с устройств с неверными часами и из офлайн-очереди попадали в правильный день, чтобы цифры совпадали с реальностью.

**Acceptance criteria**:
- [ ] Given `sent_at` = 10:00:00Z, событие `timestamp` = 09:59:00Z, сервер принял в 12:00:00Z, When запрос, Then `event_time` = 11:59:00Z.
- [ ] Given после коррекции `event_time` позже `received_at` более чем на 10 минут, When запрос, Then `event_time = received_at` и warning `timestamp_in_future_clamped`.
- [ ] Given после коррекции событие старше 168 часов, When запрос, Then reject `event_too_old` с `retryable=false`.

**Priority rationale**: Офлайн-очередь клиента — основа отказа от SDK; без коррекции дни и retention искажаются.

#### FR-003: Идемпотентность
**User story**: Как владелец, я хочу, чтобы повторные отправки одного события не завышали цифры, чтобы клиенты могли безопасно ретраить.

**Acceptance criteria**:
- [ ] Given одно и то же событие (тот же `insert_id`) отправлено трижды разными запросами, When считаются sessions и active, Then каждая метрика учитывает его один раз.
- [ ] Given два события с одинаковым `insert_id` в одном батче, When запрос, Then принято первое, warning `duplicate_insert_id_in_batch` для второго.

**Priority rationale**: Ретраи после 5xx неизбежны; без идемпотентности сверка ±5 % недостижима.

#### FR-004: Гео без хранения IP
**User story**: Как владелец, я хочу видеть страну и город пользователей, не храня их IP-адреса, чтобы соблюдать GDPR и минимизацию данных.

**Acceptance criteria**:
- [ ] Given запрос с IP из Германии, When событие сохранено, Then `country = 'DE'`, `city` заполнен по DB-IP City Lite, а IP отсутствует во всех таблицах ClickHouse, Postgres и в логах.
- [ ] Given `context.ip = "203.0.113.7"` от серверного источника, When запрос, Then гео вычислено по этому IP; Given `context.ip = "none"`, Then `country = ''`, `city = ''`.
- [ ] Given `context.ip` не является IP-адресом, When запрос, Then событие принято, гео пустое, warning `geo_ip_invalid`.

**Priority rationale**: Разбивка по стране и городу входит в отчёт «Аудитория»; хранение IP недопустимо по решению владельца.

#### FR-005: Rate limiting
**User story**: Как владелец, я хочу ограничить поток событий от одного приложения и одной установки, чтобы публичный ключ нельзя было использовать для засорения базы.

**Acceptance criteria**:
- [ ] Given приложение превысило 2000 событий/с (burst 4000), When следующий запрос, Then 429 `app_rate_limited` с `Retry-After`.
- [ ] Given одна установка отправила 1000 событий подряд, When приходит 1001-е, Then оно отклонено с `install_rate_limited` и `retryable=true`, остальные события батча от других установок приняты.
- [ ] Given 10 000 разных установок за одним IP (CGNAT), When каждая шлёт по 2 события, Then ни одно событие не отклонено по лимиту.

**Priority rationale**: Write-ключ публичен (вшит в приложения).

#### FR-006: PII-guard для user_id
**User story**: Как владелец, я хочу, чтобы email или телефон не попали в аналитику даже по ошибке в клиентском коде, чтобы не хранить PII.

**Acceptance criteria**:
- [ ] Given `user_id = "anna@example.com"`, When запрос, Then reject `user_id_looks_like_pii`.
- [ ] Given `user_id = "+491701234567"` или `"+7 (916) 123-45-67"`, Then reject `user_id_looks_like_pii`.
- [ ] Given `user_id = "123456789"` (Telegram ID) или UUID, Then событие принято.

**Priority rationale**: Требование минимизации данных и чистых privacy labels.

#### FR-007: Склейка «первый владелец» и unit
**User story**: Как владелец, я хочу считать людей, а не устройства, и при этом иметь режим устройств для сверки с AppMetrica.

**Acceptance criteria**:
- [ ] Given установка I 3 дня анонимна, затем на 4-й день событие с `user_id = "u1"`, When считается DAU за все 4 дня, Then все 4 дня засчитаны человеку `u:u1`, а не `i:I`.
- [ ] Given на установке I сначала был `u1`, затем `u2`, When анонимное событие I, Then оно засчитано `u:u1`; событие с явным `user_id = "u2"` засчитано `u:u2`.
- [ ] Given пользователь `u1` на двух установках, When `unit=persons`, Then DAU = 1; When `unit=installs`, Then DAU = 2.

**Priority rationale**: Решение владельца «Ретро-склейка»; режим устройств нужен для критерия успеха.

#### FR-008: Вход по passkey
**User story**: Как владелец, я хочу входить по Face ID / Touch ID без пароля и иметь способ восстановления, чтобы дашборд был защищён от фишинга.

**Acceptance criteria**:
- [ ] Given нет ни одного passkey, When `appmetrica admin passkey-link`, Then печатается ссылка `https://appmetrica.online/setup/<token>`, действующая 15 минут и один раз.
- [ ] Given валидная ссылка, When регистрация passkey на S-02, Then создан owner, passkey и сессия `am_session`; повторное открытие ссылки → 410 `setup_token_expired`.
- [ ] Given зарегистрированный passkey, When вход на S-01, Then cookie `am_session` (HttpOnly, Secure, SameSite=Lax) и редирект на `next` или `/`.
- [ ] Given единственный passkey, When попытка удалить его в `/settings`, Then 409 `last_passkey`.

**Priority rationale**: Дашборд и документация доступны только владельцу.

#### FR-009: Управление приложениями
**User story**: Как владелец, я хочу создавать, переименовывать, архивировать и удалять приложения, чтобы портфель отражал реальные продукты.

**Acceptance criteria**:
- [ ] Given форма S-04 с именем «Notes iOS», платформой `ios`, TZ `Europe/Berlin`, When сохранить, Then 201 с приложением и первым write-ключом, редирект на S-10.
- [ ] Given имя уже существует (без учёта регистра), Then 409 `app_name_taken`.
- [ ] Given архивное приложение, When приходит событие, Then 403 `app_archived`; приложение скрыто в портфеле, пока не включён «Показать архивные».
- [ ] Given удаление с вводом неверного имени, Then 409 `confirm_name_mismatch`; с верным — 202 и deletion request `subject_type=app`.

**Priority rationale**: Портфель строится из списка приложений.

#### FR-010: Write-ключи pk_
**User story**: Как владелец, я хочу иметь несколько активных ключей на приложение и отзывать старые, чтобы ротировать ключ без поломки старых версий.

**Acceptance criteria**:
- [ ] Given приложение с двумя активными ключами, When события приходят с любым из них, Then приняты.
- [ ] Given ключ отозван, When через ≥ 15 секунд приходит событие с ним, Then 401 `invalid_app_key`.
- [ ] Given экран S-11, When владелец смотрит ключ, Then он виден целиком (публичный) и копируется в один клик.

**Priority rationale**: Ключ вшит в бинарники приложений — нужна ротация.

#### FR-011: Read API ключи sk_
**User story**: Как владелец, я хочу выпускать секретные ключи со scope `read` и `delete`, при необходимости на одно приложение, чтобы безопасно использовать Read API в скриптах.

**Acceptance criteria**:
- [ ] Given создание ключа, Then секрет `sk_…` показан один раз, в БД хранится только HMAC-хэш и префикс.
- [ ] Given ключ со scope `read`, When `POST /v1/apps/{app_id}/deletion-requests`, Then 403 `insufficient_scope`.
- [ ] Given ключ привязан к приложению A, When запрос к приложению B, Then 404 `app_not_found`.

**Priority rationale**: Read API в MVP по выбору владельца.

#### FR-012: Портфель
**User story**: Как владелец, я хочу открыть дашборд и сразу увидеть таблицу всех приложений с ключевыми цифрами, чтобы за минуту понять состояние портфеля.

**Acceptance criteria**:
- [ ] Given 4 активных приложения, When открыт `/`, Then таблица из 4 строк с колонками: приложение, DAU сегодня, DAU за дату (по умолчанию вчера), Δ % к тому же дню прошлой недели, новые, сессии, D1, D7, спарклайн 30 дней.
- [ ] Given клик по заголовку «Δ», Then сортировка по убыванию/возрастанию; клик по строке → `/apps/[appId]`.
- [ ] Given когорта D7 ещё не наступила, Then ячейка показывает «—».
- [ ] P95 ответа `GET /v1/portfolio` ≤ 1 с при 100k DAU.

**Priority rationale**: Главная идея продукта — «один экран с главным по всем приложениям».

#### FR-013: Аудитория
**User story**: Как владелец, я хочу видеть активных, новых, сессии и длительность за период с разбивками и фильтрами, чтобы понимать динамику каждого продукта.

**Acceptance criteria**:
- [ ] Given период «последние 7 дней» (default), Then 4 KPI-карточки (Активные, Новые, Сессии, Ср. длительность) с Δ к предыдущему периоду при включённом сравнении.
- [ ] Given детализация `hour|day|week|month`, Then график метрики с точками в TZ приложения; почасовая детализация доступна для диапазона ≤ 7 дней.
- [ ] Given фильтр `platform=ios&platform=android&app_version=3.1.0`, Then OR внутри измерения, AND между измерениями; состояние фильтров в URL.
- [ ] Given вкладка разбивки `country`, Then таблица «значение / количество / доля» топ-50.
- [ ] График DAU/WAU/MAU по дням периода.

**Priority rationale**: Отчёт «Аудитория» выбран владельцем как обязательный для MVP.

#### FR-014: Retention
**User story**: Как владелец, я хочу видеть классический retention по дневным и недельным когортам, как в AppMetrica, чтобы сравнивать удержание версий и платформ.

**Acceptance criteria**:
- [ ] Given когорта 100 человек с first_seen 2026-11-01 и 38 из них с событиями 2026-11-02, Then ячейка D1 = 38 %.
- [ ] Given `cohort_granularity=week`, Then столбцы W0..W12 по ISO-неделям.
- [ ] Given период ещё не наступил, Then ячейка пустая (null), а не 0 %.
- [ ] Heatmap — HTML-таблица с цветовой шкалой, копируемая в буфер обмена.

**Priority rationale**: Retention выбран владельцем как обязательный для MVP.

#### FR-015: Realtime
**User story**: Как владелец, я хочу в день релиза видеть, сколько людей активны прямо сейчас и какие события приходят, чтобы проверять интеграцию.

**Acceptance criteria**:

- [ ] «Активны сейчас» = люди с `session_start` за последние 30 минут без `session_end` той же сессии.
- [ ] Кнопка «Пауза» останавливает polling; лента — 50 последних событий.

**Priority rationale**: Выбран владельцем как обязательный для MVP.

#### FR-016: Профили
**User story**: Как владелец, я хочу найти устройство или пользователя по `install_id` / `user_id` и увидеть его сессии, чтобы разбирать обращения пользователей и отлаживать интеграцию.

**Acceptance criteria**:

- [ ] Given профиль, Then лента сессий (дата, начало, длительность, версия, установка) с подгрузкой по 100 через `before`.
- [ ] Given несуществующий идентификатор, Then «Ничего не найдено» и подсказка формата.

**Priority rationale**: Выбран владельцем как обязательный для MVP.

#### FR-017: Экран «Интеграция»
**User story**: Как владелец, я хочу видеть ключ, готовые сниппеты и состояние приёма событий по приложению, чтобы подключать продукты за минуты и замечать сломанную интеграцию.

**Acceptance criteria**:

- [ ] Given первое событие принято, Then статус «Первое событие получено <время>» ≤ 10 секунд.
- [ ] Given события за 24 ч, Then почасовой график accepted/rejected, таблица причин отказа (код, количество, последний пример payload без IP, сообщение) и таблица по `app_version`.

**Priority rationale**: Без SDK главная проблема — тихо сломанная интеграция; владелец выбрал «Да, полный».

#### FR-018: Публичный Read API

#### FR-019: GDPR-удаление
**User story**: Как владелец, я хочу удалять все данные конкретного пользователя приложения по API и кнопкой, чтобы исполнять запросы на удаление.

#### FR-021: Системные проверки и алерты

- **Хранение IP-адресов, даже усечённых** — причина: решение владельца «Страна + город, IP не храним».
- **Семплирование отчётов** — причина: объём (до 150 млн событий/мес) позволяет точные `uniqExact`.

## 7. Non-Functional Requirements (NFR)

### 7.1. Performance
- Page load (P95): < 2500 ms LCP на страницах дашборда (desktop, NFR-006); INP ≤ 200 ms; initial JS ≤ 250 KB gzip.
- API response time (P95): < 1500 ms для отчётов на диапазоне 90 дней при 100k DAU; < 1000 ms для портфеля (NFR-003); ingest P99 ≤ 500 ms при 500 rps, включая ожидание подтверждения вставки (NFR-001).
- Time to interactive: < 3 s на портфеле при холодном кэше; событие видно в realtime ≤ 10 s после ответа 200 (NFR-004).

### 7.2. Scalability
- Target DAU на 12 мес: 100 000 суммарно по портфелю.
- Peak RPS: 500 запросов/с на ingest (≈ 2000 событий/с), до 10 запросов/с на Read API.
- Data volume (12 мес): ≈ 182 млн строк `events` в год при 100k DAU и одних системных событиях (≈ 9 ГБ сжатых, ≈ 19 ГБ за 25 месяцев — см. 05-data-model.md); верхняя граница с кастомными событиями (P1, FR-102) — 1–2 млрд строк и ≈ 100 ГБ в год, ≈ 210 ГБ за 25 месяцев при 1,92 ТБ полезного места RAID1.

### 7.3. Reliability
- Uptime SLA: 99.9 % в месяц для ingest (NFR-002); для дашборда — best effort.
- RPO: 24 ч при катастрофе сервера (ежедневные бэкапы в S3); 0 потерь для подтверждённых событий при штатной работе (NFR-005).
- RTO: 4 ч (новый сервер Hetzner + восстановление из S3 по runbook в [21-ops-runbooks.md](./21-ops-runbooks.md)).

### 7.4. Security
- Authentication: passkey (WebAuthn, resident key, user verification required) для дашборда; `pk_` (публичный write) для ingest; `sk_` (Bearer, HMAC-хэш в БД) для Read API.
- Authorization model: single-user; scopes `read` / `delete` и привязка `sk_` к приложению.
- Data at rest: шифрование диска не используется на уровне ОС (выделенный сервер, RAID1); бэкапы в Hetzner Object Storage — server-side encryption провайдера, бакеты приватные, versioning + object lock.
- Data in transit: TLS 1.3+ (Traefik, Let's Encrypt HTTP-01) для всех трёх доменов.
- PII storage: да — `install_id`, `user_id` (непрозрачный, PII-guard), страна, регион, город, модель устройства; IP — нет нигде (NFR-007).
- Compliance: GDPR (ЕС) — минимизация, удаление, сроки хранения; 152-ФЗ — открытый вопрос о локализации данных граждан РФ.

### 7.5. Accessibility
- WCAG: AA (WCAG 2.2, NFR-008).
- Screen readers: yes — таблицы с `<th scope>`, графики дублируются таблицей данных, проверка VoiceOver на S-03, S-05, S-06.
- Keyboard navigation: yes — все элементы доступны с клавиатуры, видимый фокус, без ловушек фокуса.
- Dynamic type / large fonts: yes — масштаб браузера до 200 % без потери функциональности на ширине 1280px.

### 7.6. Internationalization
- Языки на старте: русский (интерфейс и документация).
- Языки через 6 мес: русский (английский — P2, FR-204).
- RTL support: no.

### 7.7. Observability
- Error tracking: структурированные JSON-логи `log/slog` с `request_id`, без IP; Sentry не используется (single-user; ошибки видны в логах Dokploy и на вкладке «Система»).
- Logs retention: 14 дней в Docker json-file (ротация 50 МБ × 5 файлов на контейнер).
- Metrics: Prometheus `/metrics` на `:9090` каждого Go-процесса (наружу не публикуются), читаются worker-ом для `system_check`.
- Uptime monitoring: healthchecks.io dead-man switch (ping каждые 5 мин от worker) + Telegram-алерты worker-а + уведомления Dokploy о деплоях и бэкапах.

### 7.8. Cost
- Target инфра cost на 1k DAU: < $300/мес (≈ 266 €/мес — фиксированная стоимость одного сервера).
- Target на 10k DAU: < $300/мес (тот же сервер; запас до 100k DAU и 25 месяцев хранения).
